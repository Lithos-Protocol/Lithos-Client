Batching and orders

Advanced

Assumes you know what a DEX order box is and how mempool chaining works. Start with Block packages if not.

A batcher finds orders that other people have placed, executes them correctly, and keeps the executor fee the order's own script pays. This page covers the batching block, which configures the two batchers, and lithosdex.orders, which sets the fees on orders you place.

How a batcher earns​

An order is a box whose script pays a fixed executor fee to whoever fills it correctly. The contract fixes the price bound, the owner's reward script and the fee. You choose the moment and keep the fee.

Nothing about filling an order needs your own capital. No path selects a wallet box: a run is funded entirely by the orders it fills, and its takings chain from one execution to the next.

There are two ways to execute, and the difference is the miner fee:

Candidate, in your own blockBroadcast, through the mempool
Miner feeNonemin(order cap, broadcastMinerFeeCeiling) out of the executor fee
Pool boxConfirmed onlyFollowed to its mempool tip
Competing spendsSupersededNever displaced
ShipsOn for LithosDex, off for ErgoDEXOff for both

In your own block an execution pays no fee at all, so the whole executor fee is revenue. A broadcast has to pay the network, so its revenue floor is higher.

Two switches must both be on for candidate execution

batching.<name>.enabled runs the batcher, which scans and can broadcast. Inserting executions into your own block additionally needs stratum.candidate.blockTransactions and the matching stratum.candidate.sources.<name> source. A batcher runs whether or not this node mines, because broadcasting needs no stratum.

These keys exist under both batching.ergodex and batching.lithosdex:

deniedPools also exists on both as a list of pool NFT ids never to execute against. It defaults to empty and is not validated at startup. Ids are compared lowercased.

Executing unconfirmed orders​

An order placed seconds ago is worth more than one that has sat for a block, so both batchers read the mempool themselves and carry the transaction that placed an order ahead of the execution. That is where most of the revenue is, and three rules keep it safe.

A placement must be a wallet's, not a bot's. Its inputs must be uncontested and spendable by one key alone, with no data inputs and no pool output. A transaction that executes an order and places a new one fails this test, so a competitor's work is never carried.

Depth is bounded by maxAncestorTxs. Each carried transaction is one more that can invalidate your whole run.

Spam is bounded per creating transaction, not per order. Order boxes are cheap to make and transactions are not, so unconfirmed orders are taken in rounds across the transactions that created them. maxMempoolOrdersPerTx caps what any one transaction contributes, so a transaction carrying hundreds of order boxes takes four places rather than all of them.

The two maxUnbuildable settings work the same way for failures. A run stops after maxUnbuildablePerRun failures in total, and passes over a single transaction's remaining orders after maxUnbuildablePerTx of them fail, so one spam transaction cannot use up the whole run's attempts.

What a failure costs you is fees, never funds

An order that cannot be built is passed over and skipped for an hour. A run that overruns its budget offers nothing. An unbuildable order leaves the owner's funds in their own refundable box. Each failure is one wasted signature, which is why the bounds exist at all.

ErgoDEX only​

ErgoDEX executes against many pools, so it has two settings LithosDex does not need:

SettingDefaultRangeWhat it does
batching.ergodex.maxTrackedPools2561 to 1024Pools tracked, newest first
batching.ergodex.maxPoolAgeBlocks201601 to 10000000Skip pools whose current box was included more than this many blocks ago

The ErgoDEX batcher covers MewDex too, since MewDex is the same contracts under a different interface.

Its candidate source ships off. The batcher itself ships on, so it scans, but nothing reaches your block until you enable stratum.candidate.sources.ergodex.

LithosDex only​

LithosDex executes against the single ERG to LIT pool, so it needs no pool tracking:

SettingDefaultRangeWhat it does
batching.lithosdex.autoFlushtruetrue or falseClose each candidate run with a flush, moving the pool's pending fees to the vault

A flush is what lets liquidity providers claim the fees the pool has accumulated. It pays you nothing and costs nothing in a block besides the small space it takes up in size and cost. It is enabled by default to ensure permanent fees are moved quickly. It is never broadcast, because a broadcast flush would pay a network fee for no return.

Fees on orders you place​

The lithosdex.orders block sets the fees carried by orders you place through the API or web panel, when the request does not name its own:

SettingDefaultRangeWhat it does
lithosdex.orders.executorFeeNanoErg3000000Checked per requestWhat your order pays whoever fills it
lithosdex.orders.maxMinerFeeNanoErg1000000Checked per request, must be below the executor feeMost of that fee a filler may spend as a network fee

Both are paid only when a miner fills the order. A cancelled order pays neither.

These are validated per request rather than at startup, so a bad value refuses the order rather than refusing to start the client.

The default executor fee is set to clear the shipped floor of every miner running this client. Miners skip orders paying less than their minRevenueNanoErg, so an order priced below that waits indefinitely rather than failing.
